# Factory Method Pattern 정리

## 1. Factory Method 패턴 간단 정리
- **목적**: 객체 생성 로직을 서브클래스에 위임해서,  
  부모 클래스는 "무엇을 만들지는 모르고" "만드는 과정만 알고" 있도록 분리.  
- **구조**:
  - `Product`: 공통 인터페이스 (생성될 객체의 상위 타입)
  - `ConcreteProduct`: 실제 객체
  - `Creator`: 추상 클래스, `createProduct()`라는 팩토리 메소드 정의
  - `ConcreteCreator`: `createProduct()`를 구현해서 실제 객체 반환
- **장점**:
  - OCP(Open-Closed Principle) 준수 (새로운 제품 추가 시 기존 코드 수정 불필요)
  - 객체 생성과 사용을 분리
- **단점**:
  - 클래스 수가 늘어나 구조가 복잡해질 수 있음

---

## 2. 내가 헷갈렸던 부분
- 단순 팩토리(Simple Factory)는 **하나의 팩토리 클래스가 모든 객체 생성 책임을 가짐** → if/switch로 분기.
- 팩토리 메소드(Factory Method)는 **추상 팩토리 클래스**와 **팩토리 메소드**를 두고,  
  실제 어떤 객체를 만들지는 **서브클래스가 결정**.

즉,
- `K`라는 큰 팩토리에 a,b,c,d,e,f 제품을 다 넣는 게 아니라,  
- `K`를 상속한 `AFactory`는 a,b,c만, `BFactory`는 d,e,f만 담당.  
- 전체를 바꿀 필요 없이 필요한 부분만 확장/수정 가능.  

---

## 3. 왜 이름이 "팩토리 메소드"인가?
- 패턴의 핵심은 **"객체 생성을 담당하는 메소드 자체를 추상화했다"**는 것.  
- 팩토리 클래스가 추상화된 것도 맞지만,  
  더 중요한 건 **팩토리 역할을 하는 메소드(`createProduct()`)가 추상 메소드**라는 점.  
- 부모(Creator)는 "생성 메소드가 있다는 사실"만 알고,  
  실제 어떤 객체를 리턴할지는 서브클래스가 구현.

## 🎮 게임 건물/유닛 예시로 이해하기

### 왜 조건문이 남아있을까?
- 단순 팩토리(Simple Factory)라면:  
  모든 유닛을 하나의 팩토리에서 if/switch로 전부 관리 → **한 클래스에 모든 책임 집중**.
- 팩토리 메소드(Factory Method)라면:  
  건물 단위로 팩토리가 나뉨.  
  - `Barrack` → 마린, 메딕만 생성 책임  
  - `Starport` → 레이스만 생성 책임  

👉 즉, **조건문 자체는 사라지지 않을 수도 있음**.  
대신 “책임이 건물 단위로 나뉘어져” 있어서, 새로운 건물이 추가될 때 기존 코드를 수정할 필요가 없음.

### 핵심 포인트
- `Barrack` 클래스는 여전히 `if unit_name == "marine"` 같은 분기를 가질 수 있다.  
- 하지만 이는 **배럭 내부의 책임 범위**에 국한됨.  
- 새로운 건물(`Factory`, `CommandCenter`)이 생기더라도 기존 `Barrack`과 `Starport`는 수정하지 않아도 됨.  

👉 이것이 팩토리 메소드 패턴의 진짜 장점:  
**객체 생성 책임을 적절히 분리하여 OCP(개방-폐쇄 원칙)를 만족한다.**
